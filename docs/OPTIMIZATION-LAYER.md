# Optimization Layer

[English](OPTIMIZATION-LAYER.md) | [简体中文](OPTIMIZATION-LAYER.zh-CN.md)

> How external signals, human feedback and production data become prioritized
> workflow changes. This is a decision layer, not a second production system.

## What it is

The optimization layer turns four kinds of input into one ranked backlog:

| Input | Examples | Where it enters |
|---|---|---|
| External signals | X posts, GitHub repositories | `config/optimization/signals.json` (`X`, `GITHUB`) |
| Human signals | Founder review, viewer feedback | `FOUNDER`, `VIEWER` |
| Production signals | QC receipts, measured skill probes | `PRODUCTION` |
| Platform signals | views, saves, comments, consult requests | `PLATFORM_METRIC` |

It scores each candidate, applies policy, and records the decision. ContentOps
still owns the actual video pipeline; the layer never renders or publishes.

## What it is not

- not a second production system;
- not a replacement for receipts, QC or human review;
- not a place to claim metrics that do not exist. `MEASURE` and `LEARN` stay
  `BLOCKED` until a real published URL and metrics exist;
- not a GPU path. A candidate that requires a local GPU model is downgraded to
  `DEFER`.

## The loop

```
SIGNAL -> NORMALIZE -> SCORE -> DECIDE -> EXPERIMENT -> RESULT -> SHIP
   ^                                                              |
   |                                                              v
 LEARN <---------------- MEASURE <-------------------------- PUBLISH
```

- **SIGNAL**: capture the post/repo/feedback/receipt with a link and metrics.
- **NORMALIZE**: map it to an affected stage (`body`, `claims`, `audio`,
  `captions`, `architecture`, `measurement`, `feedback`).
- **SCORE**: `priority = 2*impact + evidence - effort - risk`.
- **DECIDE**: `ADOPT`, `EXTEND`, `BUILD`, `DEFER`, `REJECT`.
- **EXPERIMENT**: one variable per run; the result is a receipt.
- **SHIP**: a workflow change with tests.
- **MEASURE**: a real published URL plus platform metrics.
- **LEARN**: Founder/viewer feedback updates the next cycle's signals.

## Decision rules

| Decision | Meaning |
|---|---|
| `ADOPT` | Use an existing capability, with a linkable GitHub source and evidence |
| `EXTEND` | Use part of an existing capability without installing a second stack |
| `BUILD` | Implement a missing, owned capability |
| `DEFER` | Worth doing, but blocked by a credential, data, or a later stage |
| `REJECT` | Would duplicate the production system or violate policy |

An `ADOPT` is downgraded to `DEFER` when any of these is true:

- no linkable GitHub repository;
- `evidence < min_evidence_score` (2 by default);
- `gpu_required: true`.

The downgrade and its reasons are recorded in the report. A proposal is not
silently rewritten.

## Files

```
config/optimization/
  policy.json          # weights, floors, allowed decisions, flywheel stages
  signals.json         # X/GitHub/founder/production/platform inputs
  backlog.json         # candidates, declared scores and decisions
  flywheel.json        # current cycle state and blocked stages
  backlog-evaluated.json  # generated by --write
  optimization-report.json # generated by --write
scripts/optimization_cycle.py  # CLI
src/contentops/optimization/   # scoring, validation, ranking
tests/test_optimization_layer.py
```

## Commands

```powershell
python scripts/optimization_cycle.py            # markdown report
python scripts/optimization_cycle.py --json     # machine-readable report
python scripts/optimization_cycle.py --write    # write evaluated artifacts
python scripts/optimization_cycle.py --flywheel # current cycle state
```

Exit code `2` means a malformed signal/candidate or a policy refusal.

## Adding a signal

1. Append a signal with `source`, `captured_at`, `title`, `observation`,
   `affected_stage`, `evidence` and optional `metrics`.
2. Add a candidate with `signal_ids`, scores 1–5, `gpu_required` and a declared
   decision.
3. Run `python scripts/optimization_cycle.py` and read the effective decision.
4. Only then write code. A candidate that was downgraded to `DEFER` is not an
   instruction to build it now.

## Measurement handoff

After manual publishing:

1. fill `publish-receipt.json` with the real URL and timestamp;
2. fill `metrics-snapshot.json` with rows from the platform's own read-only data;
3. add `PLATFORM_METRIC` and `VIEWER` signals;
4. run the cycle; the next backlog reflects real use, not guesses.
