## Modality is not asset kind

The plan did not anticipate how little the three receipt schemas agree:

|                          | speech                          | image                  | video                  |
|--------------------------|---------------------------------|------------------------|------------------------|
| `schema` field           | **absent**                      | `...image-receipt/v1`  | `...video-receipt/v1`  |
| asset digest field       | `normalized_sha256` / `raw_sha256` | `output_sha256`        | `output_sha256`        |
| `generated`              | **absent**                      | `true`                 | `true`                 |
| `evidence_capable`       | **absent**                      | `false`                | `false`                |
| `AssetKind`              | **none**                        | `GENERATED_IMAGE`      | `GENERATED_VIDEO`      |
| registered in registry   | **never**                       | by the CLI script      | by the provider        |

So `MediaModality` (SPEECH / IMAGE / VIDEO) is introduced as a dimension
**separate** from `AssetKind`, and `MediaAssetEnvelope.asset_kind` is optional and
`None` for speech. Inventing `GENERATED_SPEECH` inside the visual evidence enum
was rejected: it would put a non-visual into a visual enum and imply speech has an
evidence boundary it does not have.

`AssetKind` remains the single owner of the evidence truth table. The converged
layer *asks* it rather than restating it.

## One validator, three adapters

`validate_media_asset(envelope, adapter)` owns only what is genuinely common:
file existence, receipt existence and parse, digest agreement, fingerprint,
subscription-only billing, targeted credential and task-privacy invariants, review
state, fallback explicitness, and lineage.

Adapters supply what differs: accepted schema, which receipt field holds the
digest, whether `generated` / `evidence_capable` apply, the registry kind, and the
modality's own technical QC. One dispatch table at a protocol boundary, and a test
asserts the common path contains **no** `if modality ==` branch.

Two rules the implementation added that the plan did not mention:

- a **provider generation** must declare its modality's schema; a **non-generated**
  asset must not, because nothing's API produced it
- a **missing** `technical_qc` fails a generation but is *not applicable* to an
  import or a transform, because no provider ran and there is nothing to report

## Immutability, derived assets, and the transform receipt

Provider assets stay immutable. `AudioPolicy` is applied by producing a
**derived asset** plus a `contentops.media-transform/v1` receipt that names the
source digest, so provenance stays a chain rather than being flattened.

| Policy  | Derived asset | Audio in output | Narration required |
|---------|---------------|-----------------|--------------------|
| `KEEP`  | **none** — the original is reused | present (recorded) | no |
| `MUTE`  | yes | absent | no |
| `REPLACE` | yes | absent | **yes** |

`KEEP` deliberately writes nothing. Bytes that did not move must not acquire
provenance implying they did. `REPLACE` does not mux narration — composition does,
from a deterministic track, so this step cannot produce a silent mix.

Video streams are **copied**, not re-encoded, when audio is dropped: re-encoding
would change the picture, so a "MUTE" would silently degrade the visuals.

## Capability registry

Justified now because the execution router must resolve executors by capability
rather than vendor name. No vendor word appears in any capability identifier.
Registration takes a **callable**, not a provider object, so the registry cannot
hold a credential or billing state.

Status is not inferred from "the code exists":

| Capability | Status | Evidence |
|---|---|---|
| `SPEECH/NARRATION` | `VERIFIED` | PR #24 |
| `IMAGE/GENERATED_SUPPORT_VISUAL` | `VERIFIED` | PR #25 |
| `VIDEO/H3_T2VA` | `VERIFIED` | M2.0 real task |
| `VIDEO/H3_I2VA` | `VERIFIED` | M4 real task |
| `VIDEO/H3_FL2VA`, `H3_L2VA`, `H3_REF2VA`, `H3_MAX` | `DOCUMENTED_BUT_NOT_TESTED` | fixtures only |
| `VISUAL/REAL_EVIDENCE`, `VISUAL/DIAGRAM` | `MANUAL_ONLY` | operator / local render |

A `VERIFIED` capability **cannot be constructed without citing evidence**, which is
what keeps the table from decaying into a wish list.

## Quota policy, not a cost model

`MediaQuotaPolicy` holds explicit operator values. The weekly floors are **chosen**,
not derived from the observed ~7pp H3 delta — that observation is an input to
budgeting, not a price. The provider exposes percentages only, and the test suite
asserts no configured value equals 7.

`QuotaScheduler` takes **one** snapshot and applies one policy to every action,
because all three modalities share one account plan. Priority is fixed by policy:
reuse → evidence → narration → deterministic → generated image → generated video.
Video goes last because it is the most expensive thing ContentOps does and the
least load-bearing for a truthful video.

The scheduler **does not authorise anything**. Every provider still runs its own
`BillingGuard` immediately before its call.

## Evidence-first execution

A claim-bearing beat resolves only to `REAL` / `SCREENSHOT` / `SCREEN_RECORDING`.
If the required material is absent the beat returns
`EVIDENCE_ASSET_REQUIRED` — a structured refusal, not an exception and not a
substitute. The locator reports `MISSING_REAL_ASSET` or `NEEDS_CAPTURE`.

Importing real material writes a `contentops.media-import/v1` receipt. An import
with only a digest would be the weakest link in the chain, and "no receipt, no
record" is the standing rule.

## Converged gate

`BLOCKED` → `DEGRADED_FALLBACK` → `PENDING_HUMAN_REVIEW` → `PRODUCTION_READY`,
plus `REJECTED`. Technical success is not approval: the gate refuses to reach
`PRODUCTION_READY` without a recorded human decision, and the **validator** refuses
a receipt claiming `production_ready: true` while still pending review.

## Manifest as the single asset list

`contentops.media-manifest/v1` is the only list composition and final QC read. It is
an **index**: modality-specific detail stays in the receipts, which is why a
manifest that copied every receipt field would become a second source of truth.

Deterministic: assets sorted by `asset_id`, fixed key order, and **no timestamp in
the body** — receipts already record when things happened, and a timestamp would
make every build differ for no informational gain. An asset with no gate decision,
or a duplicate `asset_id`, is refused rather than admitted.

## Composition reuses the pinned Easel path

```
manifest → thin manifest-to-storyboard translation → pinned Easel V1 → final.mp4 → qc_video
```

No second compositor was built. `assemble_easel.run()` and `qc_video.qc()` are
called as they are, and `qc_video` reads the same storyboard the manifest produced,
so the final QC is a check of the manifest rather than a separate opinion.

## What the technical integration proves

`scripts/m45_media_integration.py` produces one local, fixture-driven
`final.mp4` proving `registry → manifest → compose → final QC` with **zero
provider calls**. Every asset is a deterministic fixture, labelled as such in its
receipt, in the manifest header and in the integration report.

It does **not** prove real `SourceArtifact` ingestion, `Claim Ledger`
completeness, Founder approval, a production golden, or three consecutive
production builds. The output is `production_ready=false` /
`PENDING_FOUNDER_REVIEW`, and nothing in the code path can report otherwise.
